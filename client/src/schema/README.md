# Schema toolkit — building the annotation editor against the LinkML model

This document explains how the editing client (`/edit`) turns the project's LinkML
schema into everything a form needs: **static types**, **runtime validation**, **type-safe
unmarshalling** of API responses, and **blank instances** for new entries.

It is written for whoever builds the annotation UI — human **or** an assisting LLM. If you
are about to write an editor component, read this first; the recipes below are meant to be
copied.

> **Status:** this is a standalone doc for review. It will be folded into the broader
> project documentation later. A few things are still open — see [Open questions](#open-questions).

---

## The pieces

Everything lives under `client/src/schema/` and is imported via the `@/` alias
(`@/schema/*`).

| File | What it is | Edit by hand? |
|---|---|---|
| `index.ts` | **Generated** TypeScript interfaces + enums for every entity | ❌ generated |
| `schema.json` | **Generated** JSON Schema of the same model (Ajv-ready) | ❌ generated |
| `document.ts` | `schemaDocument` — `schema.json` typed once | ✅ |
| `types.ts` | Generic type helpers: `Create<T>`, `Update<T>`, `Draft<T>` | ✅ |
| `variants.ts` | Schema transforms: `toInputSchema`, `toDraftSchema` | ✅ |
| `validation.ts` | Ajv helpers (`compile`, `parseAs`) + reference validators | ✅ |
| `empty.ts` | `makeEmpty` (blank instances) + `updateAt` (deep update) | ✅ |

`index.ts` and `schema.json` are **generated from the LinkML schema** and carry a
DO-NOT-EDIT notice. Regenerate them with [`make schema`](#regenerating); never hand-edit.

---

## Mental model

The LinkML schema (`server/src/zapp_atlas/schema/…schema.yaml`) is the **single source of
truth**. From it we generate two client artifacts:

- **`index.ts`** — the TypeScript *types* (compile-time shapes, enums, field descriptions).
- **`schema.json`** — a JSON Schema (runtime *constraints*).

Everything else in the toolkit is a small, generic helper over those two — no per-entity
code is written or generated by hand. The three things a form needs map cleanly:

| Need | Ingredient |
|---|---|
| **1. Static types** (fields, enums, help text) | `index.ts` (+ `types.ts` helpers) |
| **2. Validate outgoing** create/update payloads | Ajv over the **input** schema → per-field errors |
| **3. Unmarshal incoming** API responses safely | The *same* Ajv validator as a type guard → `parseAs` |

There is intentionally **no Zod** and **no three-copies-per-entity**. Read / input / draft
are *derived* from the one generated schema by a single transform, and Create / Update /
Draft are generic type helpers.

---

## 1. Types

Import entity types and enums straight from `@/schema`:

```ts
import type { Study, Experiment, StressorChemical } from "@/schema";
import { ManufacturerEnum, SeverityEnum } from "@/schema";
```

The generated interfaces describe the **read** shape (a `Study` from the API has an `id`).
For editing you usually want a derived shape (`@/schema/types`):

```ts
import type { Create, Update, Draft } from "@/schema/types";

type NewStudy   = Create<Study>; // id optional at every level (nothing saved yet)
type StudyPatch = Update<Study>; // shallow partial, for PATCH
type StudyDraft = Draft<Study>;  // deeply optional — in-progress editing state
```

Field descriptions from the LinkML schema are preserved as JSDoc on the interfaces, so
your editor shows them on hover — good source text for field tooltips/help.

## 2. Validate outgoing payloads

Use a validator over the **input** schema (required `id`s dropped) before you POST/PATCH.
Ajv is configured with `allErrors`, so one call reports **every** problem at once — ideal
for inline field feedback:

```ts
import { validateStudyInput } from "@/schema/validation";

if (!validateStudyInput(payload)) {
  // validateStudyInput.errors: Array<{ instancePath, message, ... }>
  // e.g. { instancePath: "/experiment/0/control/0", message: "must have required property 'control_type'" }
  showFieldErrors(validateStudyInput.errors);
  return;
}
// payload is valid — safe to send
```

`instancePath` is a JSON Pointer to the offending field, so you can map an error to the
form input that owns it.

## 3. Unmarshal incoming responses

An Ajv validator is a **TypeScript type guard** (`data is T`). `parseAs` wraps that with
`.parse()`-style ergonomics: validate an API response and get it back **typed and
runtime-checked** — no unchecked `as` cast:

```ts
import { validateStudy, parseAs } from "@/schema/validation";

const res = await fetch(`/api/studies/${id}`);
const study = parseAs(validateStudy, await res.json()); // typed Study, or throws SchemaValidationError
```

## 4. Blank instances + deep updates

`makeEmpty` builds a blank entry from the schema — never hand-maintain an "empty object":

```ts
import { schemaDocument } from "@/schema/document";
import { makeEmpty, updateAt } from "@/schema/empty";

const blank = makeEmpty<Study>(schemaDocument, "Study");
// → { publication: "", lab: "", annotator: [], experiment: [] }
```

Value policy: multivalued → `[]`, string scalars → `""`, everything else (numbers, enums,
nested objects) is left unset until the user fills/opens it. The result is a `Draft<T>`, so
it **won't pass input validation until required fields are filled** — that's the point.

`updateAt(root, path, value)` sets a deep path immutably (clones along the path), and
`makeEmpty` also mints new nested rows:

```ts
// edit a deep field
setStudy((s) => updateAt(s, ["experiment", 0, "control", 0, "control_type"], "wildtype"));

// "Add experiment"
setStudy((s) =>
  updateAt(s, ["experiment"], [...(s.experiment ?? []), makeEmpty(schemaDocument, "Experiment")]),
);
```

## State-ownership convention

The legacy editor used **one** empty root object, deeply updated — keep that shape:

- The **form root** calls `makeEmpty` **once** and owns the whole draft in a single state.
- It passes each child a **slice** (`value`) and an **`onChange`** (which does an
  `updateAt` on the root).
- **Leaf/field components do not call `makeEmpty`.** They only render their slice and emit
  changes. `makeEmpty` is reused only to append a new array row.

This keeps one source of truth for the entry, makes validation a single call on the root,
and avoids every component re-doing the empty-instance dance.

## Worked example

A leaf widget plus the root that owns state. Plain React — **no form library is imposed**
(see [Open questions](#open-questions)); if the team adopts one later, its Ajv/JSON-Schema
resolver plugs into these same validators.

**Leaf — edits a `StressorChemical` slice, enum-driven dropdown:**

```tsx
import type { StressorChemical } from "@/schema";
import { ManufacturerEnum } from "@/schema";
import type { Draft } from "@/schema/types";

type Props = {
  value: Draft<StressorChemical>;
  onChange: (next: Draft<StressorChemical>) => void;
};

export function StressorChemicalFields({ value, onChange }: Props) {
  const set = (patch: Partial<Draft<StressorChemical>>) => onChange({ ...value, ...patch });

  return (
    <fieldset>
      <label>
        Chemical name
        <input
          value={value.chemical_name ?? ""}
          onChange={(e) => set({ chemical_name: e.target.value })}
        />
      </label>
      <label>
        Manufacturer
        <select
          value={value.manufacturer ?? ""}
          onChange={(e) => set({ manufacturer: e.target.value || undefined })}
        >
          <option value="">—</option>
          {Object.values(ManufacturerEnum).map((m) => (
            <option key={m} value={m}>{m}</option>
          ))}
        </select>
      </label>
    </fieldset>
  );
}
```

**Root — owns the draft, validates, submits, unmarshals:**

```tsx
import { useState } from "react";
import type { Study } from "@/schema";
import { schemaDocument } from "@/schema/document";
import { makeEmpty, updateAt } from "@/schema/empty";
import { validateStudy, validateStudyInput, parseAs } from "@/schema/validation";
import { StressorChemicalFields } from "./StressorChemicalFields";

// Where the first stressor lives in a Study (root owns the whole draft).
const STRESSOR_PATH = ["experiment", 0, "exposure_event", 0, "stressor", 0] as const;

export function StudyForm() {
  const [study, setStudy] = useState(() => makeEmpty<Study>(schemaDocument, "Study"));

  async function submit() {
    if (!validateStudyInput(study)) {
      // render validateStudyInput.errors against fields (see §2)
      return;
    }
    const res = await fetch("/api/studies", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify(study),
    });
    const saved = parseAs(validateStudy, await res.json()); // typed, runtime-checked Study
    console.log("saved study", saved.id);
  }

  return (
    <form onSubmit={(e) => { e.preventDefault(); void submit(); }}>
      {/* Root passes a slice + an onChange that does updateAt on the root. */}
      <StressorChemicalFields
        value={study.experiment?.[0]?.exposure_event?.[0]?.stressor?.[0] ?? {}}
        onChange={(next) => setStudy((s) => updateAt(s, [...STRESSOR_PATH], next))}
      />
      <button type="submit">Save</button>
    </form>
  );
}
```

## Adding a validator for another entity

The toolkit ships **one** reference validator (`Study`). You usually don't need more:
because JSON Schema resolves `$ref`s, `validateStudy` already validates the whole nested
tree (Experiments, Exposures, Observations, …).

Add a narrower validator **only** when a component needs to validate a slice **in
isolation** (e.g. inline-check one sub-form before the whole Study is assembled). The
recipe is a few lines:

```ts
import type { Experiment } from "@/schema";
import type { Create } from "@/schema/types";
import { schemaDocument } from "@/schema/document";
import { compile } from "@/schema/validation";
import { toInputSchema } from "@/schema/variants";

export const validateExperiment = compile<Experiment>(schemaDocument, "Experiment");
export const validateExperimentInput = compile<Create<Experiment>>(
  toInputSchema(schemaDocument),
  "Experiment",
);
```

`compile<T>(doc, defName)` pairs a `$defs` entry with its TS type; both come from the same
LinkML source, so the pairing can't drift.

## Regenerating

`index.ts` and `schema.json` are generated. After the LinkML schema changes:

```sh
cd server && make schema
```

This regenerates the pydantic/sqla artifacts **and** the client `index.ts` + `schema.json`.
Do not hand-edit either generated file — your changes will be overwritten.

## Dev workflow

Two processes in development (see `ARCHITECTURE.md`):

- **uvicorn** on `:8000` — serves `/api` (and the HTMX viewing app).
- **`npm run dev`** — Vite on `:5173`, base `/edit/`, with `/api` proxied to `:8000`.

`npm run build` emits `client/dist`, which the server mounts at `/edit` in production.

## Rules & gotchas

- **Never edit `index.ts` or `schema.json`.** They're generated; use `make schema`.
- **`makeEmpty` output is a draft.** It intentionally fails *input* validation until
  required fields are filled.
- **Ajv is `strict: false`, `allErrors: true`.** Non-strict because the generated schema
  carries LinkML annotation keywords and `["string","null"]`-style unions; `allErrors` so
  you get every field error in one pass.
- **No form library is imposed.** Examples use plain React state. Ajv plugs into
  `react-hook-form` (and others) via their JSON-Schema resolver if one is adopted.
- **`id` is server-assigned.** Build create payloads with `Create<T>` / `makeEmpty`; never
  invent an `id` client-side.
